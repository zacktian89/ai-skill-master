# SkillMaster 下一阶段需求

日期：2026-05-29

## 背景

当前版本已经完成第一版的基础主流程，包括 skill 导入、默认启用、项目规则、Codex 同步和技能库迁移。

但基于现有需求与代码实现的对照检查，仍存在若干会影响“完整闭环”判断的风险点。下一阶段目标不是扩展新功能，而是补齐闭环质量，确保 SkillMaster 能安全、可恢复、可诊断地管理本地 skill。

## 下一阶段目标

- 补齐链接归属和同步安全性，避免误删用户文件。
- 补齐异常恢复和诊断能力，降低状态损坏后的人工介入成本。
- 补齐关键交互缺口，使当前功能达到可交付标准。
- 补齐安装与交付验证，完成第一版真正意义上的收口。

## 需求清单

### P0-1 托管链接归属校验与安全删除

风险来源：
- 当前系统主要依据状态文件中的 `managedLinks` 判断是否为托管链接。
- 当目标目录被用户手动替换或修改后，现有删除逻辑可能误删非 SkillMaster 创建的目录。

需求说明：
- 同步、删除 skill、取消启用、项目切换导致的移除动作，都必须先校验目标是否仍是 SkillMaster 创建的托管链接。
- 只有在“路径存在、类型符合预期、目标指向当前技能库 skill 源目录”时，才允许执行删除。
- 如果状态文件记录为托管，但磁盘现场不符合托管链接条件，系统不得删除目标目录，而应记录为异常状态并提示用户处理。

验收标准：
- 用户手动把 Codex 中的托管链接替换为普通目录后，SkillMaster 不会删除该目录。
- 用户手动把托管链接改为指向其他路径后，SkillMaster 不会删除该链接。
- 出现托管记录与磁盘现场不一致时，UI 可见异常提示，且状态中保留可诊断信息。

### P0-2 Codex 同步事务化与失败恢复

风险来源：
- 当前同步流程先修改文件系统，再写状态文件。
- 一旦中途失败，可能出现磁盘现场与状态文件不一致。

需求说明：
- 同步操作需要具备最小事务语义。
- 系统应先生成完整执行计划，再按受控顺序执行，并在失败时返回可恢复结果。
- 需要定义失败后的状态策略，至少满足以下二选一：
  1. 文件系统与状态文件同时回滚到同步前。
  2. 文件系统无法完全回滚时，将状态写入一个明确的“部分完成/需修复”状态，并向用户展示修复入口。

验收标准：
- 创建第 N 个链接失败时，不会留下“状态仍显示已同步但磁盘未完成”的假成功结果。
- 删除成功、创建失败等中间态能够被系统识别并在下次启动时继续诊断。
- 手动 QA 能复现一次失败注入，并验证系统进入可恢复状态。

### P0-3 状态文件损坏后的备份恢复

风险来源：
- 当前保存状态时会写 `.bak` 备份，但读取流程没有备份恢复能力。

需求说明：
- 当主状态文件损坏或 JSON 反序列化失败时，系统应自动尝试读取最近一次备份。
- 备份恢复成功后，应明确提示用户当前已从备份恢复。
- 主状态与备份都不可用时，应提供重建状态入口，并尽量保留技能库扫描恢复的可能性。

验收标准：
- 人为破坏主状态文件后，应用可以自动从 `.bak` 恢复并正常启动。
- 主状态和备份都损坏时，应用不会直接崩溃，而会进入可处理的错误提示状态。
- Settings 中能看到当前状态文件和备份文件位置。

### P1-1 Settings 诊断中心增强

风险来源：
- 现有诊断信息过少，无法覆盖规格中的冲突、状态文件、技能库缺失等场景。

需求说明：
- Settings 中新增统一诊断区，覆盖以下场景：
  - Codex 未连接。
  - Codex 同名非托管冲突。
  - 托管记录与磁盘现场不一致。
  - 技能库路径缺失。
  - 状态文件损坏或已从备份恢复。
- Settings 中展示状态文件路径、备份文件路径、技能库路径、Codex skills 路径。
- 每条诊断信息需要具备明确文案，并区分信息、警告、错误级别。

验收标准：
- 出现冲突时，除 skill 详情外，Settings 也能看到冲突摘要。
- 用户能在 Settings 中定位状态文件位置。
- 至少覆盖 5 类异常场景，并通过手工 QA 清单验证。

### P1-2 删除 skill 前的影响确认

风险来源：
- 当前删除操作直接执行，不符合“删除前确认”的需求。

需求说明：
- 删除 skill 前必须弹出确认界面。
- 确认信息至少包含：
  - skill 名称。
  - 将删除的技能库目录。
  - 将移除的托管链接数量与目标位置。
  - 将清理的项目规则影响范围。
- 用户取消后不得发生任何文件或状态变更。

验收标准：
- 删除前必须经过确认操作。
- 确认弹窗中能看到受影响的托管资源摘要。
- 取消删除后，状态文件和磁盘内容不变。

### P1-3 首次启动资源初始化补齐

风险来源：
- 当前首次启动会创建状态文件，但不保证默认技能库目录已创建。

需求说明：
- 首次启动时应同时创建：
  - 应用配置目录。
  - 默认技能库目录。
  - 状态文件。
- 如果 Codex 自动检测失败，应用仍进入 Skills 首页，并在界面上展示轻量引导。

验收标准：
- 全新环境首次启动后，即使未导入 skill，也能在磁盘看到默认技能库目录。
- Codex 未检测到时，首页或 Settings 中有明确但非阻塞的引导信息。

### P1-4 当前项目上下文管理补齐

风险来源：
- 当前可以设置当前项目，但缺少清空当前项目、回到全局默认态的显式操作。

需求说明：
- Projects 视图需要提供“清除当前项目”或“回到全局默认规则”的入口。
- 顶部状态区需要明确展示当前是“某项目上下文”还是“全局默认上下文”。
- 项目切换与清空动作都应影响后续 Codex 同步计算。

验收标准：
- 用户可从任意项目上下文切回全局默认态。
- 切回全局后，再同步时，生效 skill 集合恢复为默认启用集合。

### P2-1 技能库迁移收尾与旧目录处理说明

风险来源：
- 当前迁移会复制到新目录并更新状态，但未形成完整的迁移确认与旧目录处理指引。

需求说明：
- 迁移完成后，系统应明确提示：
  - 新技能库位置。
  - 旧目录已停止被 SkillMaster 使用。
  - 是否需要重新同步 Codex。
- 如果产品决定不自动删除旧目录，界面需明确说明旧目录保留为用户自行处理。

验收标准：
- 迁移成功后，用户可以明确理解新旧目录关系。
- 迁移后重新同步的动作路径清晰可见。

### P2-2 安装包构建与交付验证

风险来源：
- 当前只验证了本地开发和测试通过，没有完成安装包构建验收。

需求说明：
- 在 Windows 与 macOS 上分别完成一次安装包构建验证。
- 记录构建产物类型、输出路径、已知限制和签名状态。
- 将安装包验证补充到手工 QA 文档与发布清单。

验收标准：
- 可以执行 `npm run tauri build` 并产出对应平台安装物。
- 文档中记录平台、产物路径、是否签名、是否可安装。

## 实施建议

建议按以下顺序推进：

1. 先完成 P0-1、P0-2、P0-3，解决数据安全与恢复问题。
2. 再完成 P1-1、P1-2、P1-3、P1-4，补齐交互和诊断闭环。
3. 最后完成 P2-1、P2-2，完成迁移体验收尾与交付验证。

## 完成定义

下一阶段完成后，应满足以下判断标准：

- SkillMaster 只会删除自己创建且可验证归属的链接。
- 同步失败不会产生不可解释的状态漂移。
- 状态文件损坏时具备自动恢复或明确重建路径。
- 用户可以在 Settings 中定位和理解主要异常。
- 删除、项目上下文、首次启动等关键交互符合设计规格。
- Windows 与 macOS 至少各完成一次安装包级验证。
